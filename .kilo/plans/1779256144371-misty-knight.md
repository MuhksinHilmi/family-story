# Rencana Implementasi: Supabase Realtime Chat + Daily Local Backup + Source Cleanup

Tujuan
- Menyajikan chat pada UI dengan dua lapisan: archive (local DB) untuk pesan lama + realtime (Supabase) untuk pesan terkini.
- Setiap hari pada 00:00 WIB, backup pesan baru dari Supabase ke Postgres lokal lalu (opsional) hapus/arsip sumber di Supabase untuk menjaga ukuran DB Supabase tetap kecil dan biaya efisien.

Ringkasan arsitektur
- Klien: menampilkan pesan dari dua sumber secara terintegrasi:
  1. Pesan historis diambil dari API lokal (Postgres archive) dan ditampilkan di atas/atau sebelum stream realtime.
  2. Pesan terkini (realtime) disubscribe dari Supabase Realtime channel; pesan baru muncul di bawah/di akhir thread.
- Server: Next.js backend (existing) menyediakan API untuk membaca archive lokal, menjalankan job backup, verifikasi, dan (opsional) penghapusan di Supabase.
- Scheduler: cron / k8s CronJob / Cloud Scheduler menjalankan skrip backup harian tepat 00:00 WIB.

Asumsi
- Supabase project sudah ada; tabel `messages` menyimpan semua pesan realtime.
- Postgres lokal (production) tersedia dan dapat diakses aman oleh backend.
- Aplikasi memiliki mekanisme autentikasi; akses ke endpoint backup/delete hanya server-side.
- Zona waktu utama: WIB (Asia/Jakarta, UTC+7).

Desain data
1) Skema tabel Supabase (source) — contoh minimal:
   - id UUID PRIMARY KEY
   - room_id TEXT
   - user_id UUID
   - content JSONB
   - type TEXT
   - created_at TIMESTAMPTZ DEFAULT now()
   - edited_at TIMESTAMPTZ NULL
   - deleted BOOLEAN DEFAULT false
   - metadata JSONB NULL
   - archived BOOLEAN DEFAULT false      -- optional (soft-delete flag)

2) Skema tabel lokal (archive) — SQL migration contoh:

   CREATE TABLE chat_message_archive (
     id UUID PRIMARY KEY,
     room_id TEXT,
     user_id UUID,
     content JSONB,
     type TEXT,
     created_at TIMESTAMPTZ,
     edited_at TIMESTAMPTZ,
     deleted BOOLEAN DEFAULT false,
     metadata JSONB,
     backup_date DATE NOT NULL,
     imported_at TIMESTAMPTZ DEFAULT now()
   );

   CREATE INDEX idx_chat_archive_backup_date ON chat_message_archive (backup_date);
   CREATE INDEX idx_chat_archive_room_created_at ON chat_message_archive (room_id, created_at);

3) Tabel job audit/log:

   CREATE TABLE backup_jobs (
     id SERIAL PRIMARY KEY,
     backup_date DATE,
     started_at TIMESTAMPTZ,
     finished_at TIMESTAMPTZ,
     status TEXT,
     supabase_count INT,
     local_count INT,
     error_text TEXT
   );

   CREATE TABLE backup_job_chunks (
     id SERIAL PRIMARY KEY,
     job_id INT REFERENCES backup_jobs(id) ON DELETE CASCADE,
     chunk_index INT,
     ids JSONB,
     status TEXT,
     processed_at TIMESTAMPTZ
   );

Alur implementasi (high-level)
- Phase A — Integrasi tampilan gabungan (archive + realtime)
  1. API endpoint: GET /api/chat/archive?room_id=&date_before=&limit=&offset= — ambil pesan dari chat_message_archive (paged) untuk room.
  2. Di client chat view: saat membuka room, load halaman awal dari archive (mis. 50 pesan terakhir dari archive untuk hari-hari sebelumnya dan awal hari ini), lalu subscribe ke Supabase realtime untuk menampilkan pesan terbaru. Pastikan ordering konsisten (created_at asc). Render archive di bagian atas dan realtime appended setelah cursor.
  3. Behavior UX: jika pesan dari Supabase memiliki ID yang sudah ada di archive (dup), dedupe dengan id.

- Phase B — Backup job harian (00:00 WIB)
  1. Scheduler memicu backup job (server-only script) pada 00:00 WIB. Jika server di UTC, cron set ke 17:00 UTC prev day.
  2. Job computes range: start = 00:00:00 (WIB) of target day, end = 00:00:00 (WIB) of (target day + 1). (Backup dapat memilih range hari sebelumnya atau hari berjalan sesuai kebijakan.)
  3. Query Supabase server-side (service_role key) untuk messages WHERE created_at >= start AND created_at < end AND archived IS NOT TRUE (atau deleted = false), order by created_at.
  4. Paginate (limit 1000) and upsert ke chat_message_archive dengan backup_date = target_day.
  5. Insert record ke backup_jobs dan per-chunk insert ke backup_job_chunks (simpan list ids sebagai JSONB) untuk audit.
  6. Setelah seluruh data diproses, hitung supabase_count dan local_count.
  7. Verifikasi: jika supabase_count === local_count (atau sesuai threshold dan checksum sampel), set backup_jobs.status = 'VERIFIED'. Jika mismatch, set status = 'FAILED' dan abort delete step.

- Phase C — (Opsional) Hapus / Arsip di Supabase
  Opsi 1 (Direkomendasikan): Soft-delete
    - Setelah VERIFIED, update supabase messages SET archived = true WHERE id IN (backed_up_ids).
    - Ini cepat, aman, bisa di-reverse jika perlu.
    - Setelah grace period (mis. 7 hari) dan pemeriksaan manual/automated, lakukan hard delete batch.

  Opsi 2: Hard-delete langsung
    - Setelah VERIFIED, lakukan delete by IDs in chunks (ukuran default 500) menggunakan supabaseServer.from('messages').delete().in('id', chunk).
    - Throttle requests dan catat hasil per-chunk.

  Keamanan: gunakan SUPABASE_SERVICE_ROLE_KEY di server; jangan expose ke client.

Implementasi detail teknis
- Environment variables (diperlukan):
  - SUPABASE_URL
  - SUPABASE_ANON_KEY (client)
  - SUPABASE_SERVICE_ROLE_KEY (server only)
  - LOCAL_POSTGRES_URL (pg connection string)
  - BACKUP_TIMEZONE (default Asia/Jakarta)
  - BACKUP_BATCH_SIZE (default 1000 untuk read, 500 untuk delete)
  - BACKUP_GRACE_DAYS (default 7)

- Skrip backup (node/ts) — pseudocode

  async function runBackup(targetDate) {
    start = startOfDay(targetDate, 'Asia/Jakarta') // inclusive
    end = addDays(start, 1) // exclusive

    jobId = insert backup_jobs(status='RUNNING', backup_date=targetDate, started_at=now())

    backedUpIds = []
    supabaseCount = 0
    cursor = null
    while (true) {
      res = await supabaseServer.from('messages').select('*')
               .gte('created_at', start)
               .lt('created_at', end)
               .order('created_at', { ascending: true })
               .limit(READ_BATCH)
               .maybeUseCursor(cursor)
      if (res.error) { mark job failed; break }
      rows = res.data
      if (rows.length === 0) break

      // Upsert to local DB in transaction
      await pgClient.transaction(async (tx) => {
        for (row of rows) {
          await tx.query(upsertQuery, [/* row fields & backup_date */])
          backedUpIds.push(row.id)
        }
      })

      supabaseCount += rows.length
      insert backup_job_chunks(job_id, chunk_index, jsonb(ids))
      cursor = res.nextCursor || null
      if (!cursor) break
    }

    // final counts
    localCount = count rows inserted for job's backup_date
    update backup_jobs set finished_at=now(), supabase_count=supabaseCount, local_count=localCount

    if (supabaseCount === localCount) update job status VERIFIED else FAILED

    if (job VERIFIED && DELETE_POLICY === 'soft') perform soft-delete per chunk
    if (job VERIFIED && DELETE_POLICY === 'hard') perform hard-delete per chunk
  }

- Delete step considerations
  - Use backedUpIds persisted in backup_job_chunks to ensure delete only IDs that were backed up.
  - Delete in chunks, retry with exponential backoff on transient errors.
  - Throttle to avoid overwhelming Supabase.

API & UI yang perlu dibuat/diubah
- API:
  - GET /api/chat/archive?room_id=&date=&limit=&offset= — membaca archive untuk room (server-side reads local DB)
  - GET /api/backups — list backup jobs (job id, date, status, counts)
  - GET /api/backups/:date — list pesan backup untuk tanggal (paged)
  - POST /api/backups/:date/verify-retry — (admin) jalankan ulang verifikasi atau retrigger delete

- UI:
  - Chat view: integrasikan archive fetch + realtime subscribe. UX:
    - Saat buka room, load latest N dari archive (mis. 50). Tampilkan loading skeleton.
    - Subscribe Supabase for inserts on that room. Merge streams (dedupe by id).
    - Provide visual separators: "History (local)" dan "Realtime" atau seamless timeline where older messages come from local and newer from realtime.
  - Admin: Backup jobs page — show history, counts, status, and manual retry/export.

Monitoring, Alerting, Observability
- Buat alert jika job FAILED or local_count != supabase_count
- Kirim notifikasi (Slack/email) pada kegagalan kritikal
- Log per-chunk details for audit

Testing &验收 (Acceptance criteria)
- Functional:
  - Setelah jalankan backup job manual untuk range contoh, semua pesan untuk range tersebut muncul di chat_message_archive dengan backup_date yang benar.
  - Dupes tidak dibuat jika job dijalankan ulang.
  - Jika terapkan soft-delete, records di Supabase bertanda archived=true setelah verified.
  - Client menampilkan pesan historis (local) dan realtime (Supabase) tanpa duplikasi.
- Performance:
  - Backup job memproses N pesan per menit sambil menjaga rata-rata latency DB Supabase < threshold.
- Safety:
  - Delete step tidak berjalan jika verifikasi gagal.

Rollback & Recovery
- Karena data archive disimpan lokal, Anda bisa memulihkan ke Supabase jika perlu (re-insert). Simpan backup_job_chunks untuk mempermudah re-import.
- Jika soft-delete dipakai, pembatalan sederhana: set archived=false untuk IDs tertentu.
